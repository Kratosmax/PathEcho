## 优先修复

### R1 · P1 · 源目录缺失会生成成功空快照，并按保留策略删除有效备份

**已动态复现。** 先正常备份含 slot.sav 的目录，将源目录改名，再调用同一 GameBackupService 手动备份。设置为最近 1 版、小时/日锚点 0。结果 returnedSuccess=true、latestFileCount=0、originalBackupStillExists=false，仅剩 1 个空版本。

调用链：

- [SnapshotStore.cs:23](../../src/PathEcho.Core/Backup/SnapshotStore.cs#L23) 正确抛出源目录不存在异常。
- [GameBackupService.cs:68](../../src/PathEcho.Core/Backup/GameBackupService.cs#L68) 把异常转入 staging 保底。
- [BackupStagingStore.cs:28](../../src/PathEcho.Core/Backup/BackupStagingStore.cs#L28) 扫描缺失源；[DirectoryScanner.cs:18](../../src/PathEcho.Core/Sync/DirectoryScanner.cs#L18) 把缺失目录视为空集合。
- 空集合与空临时副本校验通过，随后创建空快照，并在 [GameBackupService.cs:73](../../src/PathEcho.Core/Backup/GameBackupService.cs#L73) 执行保留清理。

建议：备份扫描语义必须区分“不存在”和“合法空目录”；staging 扫描前后核对源目录存在及身份，缺失进入读取源失败流程。未取得可靠源状态时禁止生成成功快照及触发保留清理。补“改名/离线/扫描期间消失 + 最小保留策略”组合回归。

### R2 · P1 · 回档后的首次增量快照可能混合回档前后的文件

**已动态复现 Core 调用链，Runtime 装配路径已源码核对。** S1={A=old,B=old}，S2={A=new,B=new}；回档到 S1 后只改 A。新快照 B 实际为 B-new，而磁盘 B 为 B-old。

[PathEchoRuntime.cs:427](../../src/PathEcho/Services/PathEchoRuntime.cs#L427) 回档仅停止/重启监听；回档产生的事件不会进入新监控。[GameBackupMonitor.cs:25](../../src/PathEcho.Core/Backup/GameBackupMonitor.cs#L25) 没有首次强制全量状态。[SnapshotStore.cs:205](../../src/PathEcho.Core/Backup/SnapshotStore.cs#L205) 对非空 changedPaths 直接沿用时间最新清单，只替换已知路径，因此未再变化的文件继续引用 S2。

建议：回档后、监控启动/重建后失效增量依据；下一次备份必须完整校准，并在成功后才清除该要求。测试同时覆盖旧内容、回档后多余文件和缺失文件，不只断言快照数量增加。

### R3 · P1 · overflow 经过节流后丢失全量补扫要求

**已动态复现控制流。** ChangedFiles-only、3 秒最低间隔，先成功备份，再同时注入普通路径变化与 overflow。尾随写入实际 received changedPaths=[known.sav]，actualFullScan=false，预期必须全量。

[GameBackupMonitor.cs:105](../../src/PathEcho.Core/Backup/GameBackupMonitor.cs#L105) 消费全量标志；首次调用因节流返回 null；[123](../../src/PathEcho.Core/Backup/GameBackupMonitor.cs#L123) 转尾随时不传原标志；[154](../../src/PathEcho.Core/Backup/GameBackupMonitor.cs#L154) 再读已清零标志，退化成路径增量。overflow 丢失的其他文件事件无法被修正，后续成功快照仍可能陈旧。

建议：全量要求随整个 pending batch 累积，只能在实际成功全量备份后消费。已有测试分别覆盖 overflow 和 trailing，缺少二者组合，见 [冒烟测试:1375](../../tests/PathEcho.SmokeTests/Program.cs#L1375)。

### R4 · P2 · 用户停止重试后，自动备份会重新进入重试

**已动态复现。** 对单次文件变化注入清理失败，确认回调每次均返回 false。没有新文件事件时仍累计 3 次停止回答、3 次 Create 调用；探针在第 3 次主动取消监控，避免无限重试。

[GameBackupMonitor.cs:225](../../src/PathEcho.Core/Backup/GameBackupMonitor.cs#L225) 将异常转换为 null，与“被节流”相同；[121](../../src/PathEcho.Core/Backup/GameBackupMonitor.cs#L121) 和 [136](../../src/PathEcho.Core/Backup/GameBackupMonitor.cs#L136) 对 null 启动并持续尾随循环。BackupRetryStoppedException 因而无法结束本批任务。

建议：返回明确的 Success/Throttled/Failed/RetryStopped 状态，只有 Throttled 进入尾随；用户停止必须终止当前批次。失败重试使用有界退避，防止立即失败路径忙循环和重复通知。

### R5 · P2 · 永久对象验真缓存会漏掉运行中的对象损坏

**已动态复现，前提为备份对象被外部改写或替换。** 同一 SnapshotStore 创建 GOOD 快照，将其 blob 改为等长 EVIL，源仍为 GOOD，再做全量备份：备份成功，但 ResolveVerifiedFileAsync 拒绝恢复。

[SnapshotStore.cs:300](../../src/PathEcho.Core/Backup/SnapshotStore.cs#L300) 对已缓存路径只看存在便复用，没有重新检查内容；[348](../../src/PathEcho.Core/Backup/SnapshotStore.cs#L348) 旧视图迁移也复用缓存，存在错误删除有效回退副本的额外风险（迁移分支未动态注入）。

建议：校验缓存限定单次操作，或采用可失效的文件身份/元数据策略；删除 legacy 回退前必须重新验真。不要用永久路径缓存代表永久内容可信。

### R6 · P2 · 更新清单和游戏目录读取没有正文停滞超时

**已用不可 Seek 停滞流动态复现。** HttpClient.Timeout 设为 100 ms，服务端模拟立即返回响应头但正文永不返回；500 ms 后更新清单和游戏目录任务都仍 pending，调用者取消后才结束。

[UpdateManifestClient.cs:21](../../src/PathEcho.Core/Update/UpdateManifestClient.cs#L21) 使用 ResponseHeadersRead，正文循环在 [46](../../src/PathEcho.Core/Update/UpdateManifestClient.cs#L46) 仅依赖调用者 token；[GameCatalogClient.cs:112](../../src/PathEcho.Core/GameCatalog/GameCatalogClient.cs#L112) 同样。HttpClient 请求超时不能覆盖已经返回响应头之后的整个正文读取。

建议：每次读取设独立停滞超时，并对每条线路设置总体截止时间；超时后释放流并切换下一线路。复用已存在于包下载器的受限复制思想，保留用户取消语义。

### R7 · P2 · 智能识别依赖的线上签名目录缺失

**已线上复核。** [默认地址定义](../../src/PathEcho.Core/GameCatalog/GameCatalogClient.cs#L14) 指向 main/config/game-catalog.json；[GitHub Contents API](https://api.github.com/repos/Kratosmax/PathEcho/contents/config/game-catalog.json?ref=main) 本轮返回 404。因此新用户没有可信缓存时智能识别不可用，不能靠现有本地 mock 测试证明线上可用。

建议：修复并验证 [游戏目录工作流](../../.github/workflows/game-catalog.yml)，经授权在受控环境生成正式签名目录，再从真实客户端获取并验签；增加线上资源健康检查。**本轮未触发工作流或向 GitHub 写入。**

工作流条件的初步怀疑已排除为“首次文件缺失”的已证实根因：隔离实验中，PowerShell if(git diff --quiet) 判断 stdout 而非退出码，无输出时不进入分支；不能把 shell 的退出码语义直接套入该条件。仍可改成 git add 后 git diff --cached --quiet 再判断 LASTEXITCODE，使无变化重跑可靠退出，但这不是本轮查实的 404 根因。

### R8 · P2 · 更新包预检只比对文本版本与文件名

**已动态复现预检层。** 只含文本冒充的 PathEcho.exe/Updater.exe、正确 marker/channel/version、没有实际主程序集和依赖的 ZIP，被 UpdatePackageValidator 接受。

[UpdatePackageValidator.cs:44](../../src/PathEcho.Core/Update/UpdatePackageValidator.cs#L44) 只检查几个文件名；[52](../../src/PathEcho.Core/Update/UpdatePackageValidator.cs#L52) 只读 version.txt/channel.txt/marker，没有读取包内真实程序集版本或关键依赖。

建议：核对真实主程序集版本、入口可执行结构、runtimeconfig/依赖及通道必要运行时。此项是误打包防护缺口，**未证明绕过清单签名、哈希验证，也不代表攻击者可上传任意未签名程序**。

### R9 · P2 · 同步目录状态不会随拔插盘或重新联网刷新

**源码已复核，未做真机拔插测试。** [SyncTaskRow:1180](../../src/PathEcho/Services/PathEchoRuntime.cs#L1180) 将两端可用性存为 readonly bool，只在构造函数执行 Directory.Exists。之后目录变成不可用，行仍显示“可用”；启动时不可用的目录恢复后，仍显示“需要检查”。依赖该值的“目录异常”筛选同样过期。

建议：暴露可刷新状态并发出属性变更；在同步前后、筛选刷新、打开目录失败及可控的后台探测时重新检查，避免在 UI 线程探测慢网络盘。目录状态用于提示，真实执行仍须处理访问失败，不能把提示状态当作操作授权或一致性保证。

## 待进一步故障注入的风险

选文件回档在 [SnapshotRestoreService.cs:180](../../src/PathEcho.Core/Restore/SnapshotRestoreService.cs#L180) 将提交后的事务清理放在回滚 try 内；若清理已部分删除原件才抛错，catch 仍会删除已恢复目标，并只恢复尚存原件，源码存在破坏性回滚路径。

本轮用 Windows 目录句柄注入占用，虽然取得句柄但没有让清理失败：250 个目标文件均保留、error=null。因此此项仅列为**高置信控制流风险，未动态复现**，不与上述已复现问题混报。建议将提交失败回滚与提交成功后的清理分开，后者失败只保留现场并报告；补稳定的清理部分成功故障注入。

## 性能与工程优化

1. **减少无效目录枚举。** [DirectoryScanner.cs:30](../../src/PathEcho.Core/Sync/DirectoryScanner.cs#L30) 递归枚举后才应用文件过滤；[SyncEngine.cs:62](../../src/PathEcho.Core/Sync/SyncEngine.cs#L62) 每次仍扫两端。建议先以大排除子树建立基准，按过滤语义安全剪枝，再评估路径级重扫；保留启动、overflow 和周期性全量兜底。本轮没有量化基准，不承诺具体提速倍数。
2. **避免云历史固定全量刷新。** [PathEchoRuntime.cs:613](../../src/PathEcho/Services/PathEchoRuntime.cs#L613) 对有关联历史的配置每 5 秒重读所有游戏历史；[SnapshotStore.cs:168](../../src/PathEcho.Core/Backup/SnapshotStore.cs#L168) 对每个版本逐文件检查内容可用性。建议清单元数据缓存、变化驱动刷新、慢/离线存储退避，按版本差异更新 UI；不能因缓存跳过回档前哈希校验。
3. **控制临时扫描缓存生命周期。** [DirectoryScanner.cs:54](../../src/PathEcho.Core/Sync/DirectoryScanner.cs#L54) 按根路径永久留存扫描字典；fallback 每次生成唯一临时根。建议事务结束清理缓存或临时源禁用持久缓存，避免常驻进程反复 fallback 后内存累积。
4. **把组合场景纳入提交前 CI。** 当前 [Release 工作流](../../.github/workflows/release.yml) 只在 v 标签执行，[游戏目录工作流](../../.github/workflows/game-catalog.yml) 只负责签名。增加不含签名密钥的 pull_request/main 构建、43 项冒烟及本报告组合回归；避免到打标签才发现错误。Runtime/WPF 关键流程需要实际行为测试，不能只依靠源码字符串契约。
5. **同步文档版本。** [README.md:3](../../README.md#L3) 和下载矩阵仍写 0.6.0，而版本源和 latest 为 0.6.2。建议从唯一版本源生成或在 CI 校验，避免遗漏补丁版本。

## 界面与用户流程建议

最终界面审查已回收，Lead 复核了下列关键控制流。独立审查成员仅阅读源码；本报告的三张新截图由 Lead 实际运行并检查，两类证据分别标注。

- **长任务进度与取消（源码确认，P2）。** [MainWindow.xaml.cs:1111](../../src/PathEcho/MainWindow.xaml.cs#L1111) 为统一操作包装器，执行期间将整个窗口 IsEnabled=false；全部同步、历史副本物化、备份发现/导入和设置迁移缺少对应的进度与用户取消入口。这是操作期间不可交互，不等于已证明 UI 线程死锁。建议复用更新窗口的进度/取消模式，只禁用会冲突的操作；提交阶段按事务安全边界禁用取消。
- **批量失败保留部分结果（源码建议，P2）。** 全部同步和发现备份批量操作中途抛错时，统一包装器仅显示整体操作失败；建议汇总每项成功/失败/跳过及已完成数量，与进度改造一起实现。
- **补充实际行为回归（测试源码确认，P2）。** [冒烟测试:930](../../tests/PathEcho.SmokeTests/Program.cs#L930) 的 UI 契约检查包含 XAML 结构断言和源码文本断言，不能证明窗口交互或 Runtime 监控交接正确。建议把回档后的监控/增量校准、备份发现关联和通知队列过期策略提取为可执行测试的服务；保留文本契约辅助检查，避免只靠临时 E2E 产物。原有 43 项并非全部 UI 行为测试。
- **版本历史最小尺寸可读性（实际截图确认，P3）。** [920×620 版本历史截图](../../temp/review/ui/History-920.png) 中，“文件数”“来源 / 状态”表头被截短，时间也无法完整显示。列定义见 [MainWindow.xaml:230](../../src/PathEcho/MainWindow.xaml#L230)。建议固定时间/数量/状态列的可读最小宽度，路径列承担弹性压缩；列总宽超过视口时保留可发现的横向滚动，完整时间可通过悬停/详情读取。不要继续缩窄关键列来塞入所有内容。
- **设置页定位和保存反馈（建议，P3）。** [920×620 设置截图](../../temp/review/ui/settings-920.png) 只显示前半设置，“保存设置”位于长滚动页底部；建议加入分类锚点或固定保存区，并标出未保存状态。当前没有验证滚动到底、键盘焦点及保存动作，不把可见首屏当作整个设置页已验收。
- **游戏页布局（实际截图确认）。** [920×620 游戏页截图](../../temp/review/ui/Game-920.png) 顶部六个操作仍可见，长目录有截断，未发现当前样本的控件重叠；仍需覆盖更多游戏、长名称与 125%/150% DPI。
- **大文件清单搜索（源码建议）。** [SnapshotFilesWindow.xaml.cs:21](../../src/PathEcho/Dialogs/SnapshotFilesWindow.xaml.cs#L21) 在 UI 线程同步构造并排序所有行，[39](../../src/PathEcho/Dialogs/SnapshotFilesWindow.xaml.cs#L39) 每键入一个字符立即全量过滤。超大快照可考虑后台生成行模型、搜索防抖、缓存标准化搜索文本，再批量切回 UI；本轮未用十万文件清单量化卡顿。
